# python-kicad-python — Omarchy ppc64le

KiCad's official IPC API bindings (`kipy`), 0.7.1, built from the PyPI sdist.
This version is required by `kicad-mcp`, which pins `kicad-python>=0.7.1,<0.8`.

## Why the protobuf wrappers are regenerated

The sdist ships `kipy/proto/*_pb2.py` generated by protobuf **5.29**, and pins
`protobuf <6`. The system runtime is protobuf **7.35.1** (`python-protobuf`
35.1). The runtime allows gencode one major version older (with a warning);
two majors older is a `VersionError` at import.

`prepare()` therefore:

- **Fetches the API protos.** Only `api/proto` is taken from KiCad commit
  `2db9e5a72b`, tag 10.0.1. That is the version recorded in
  `kipy/kicad_api_version.py`.
- **Regenerates the wrappers** with the system `protoc` (`--python_out`,
  `--pyi_out`).
- **Rewrites imports** to the relative form upstream gets from protoletariat:
  one dot per directory level below `kipy/proto`, plus one.

`kicad-python-system-build.patch` drops the `build.py` hook, which would
regenerate the wrappers from a git submodule absent from the sdist. It also
relaxes the protobuf pin.

The sdist also carried five wrappers that are not in KiCad 10.0.1:
`board_jobs`, `generators`, `jobs`, `wizards` and `schematic_jobs`. Their
gencode stamps differ from the rest, so they look left over from an older
generation run. Nothing in kipy imports them, and they are not regenerated.

`build()` asserts the result (bq builds `--nocheck`):

- every `kipy.proto` module imports under the system protobuf with warnings as
  errors;
- `from kipy import KiCad` works;
- a `Track` message round-trips.
